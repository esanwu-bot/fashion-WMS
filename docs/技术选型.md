# RFID 服装零售 WMS · 技术选型

> 版本 v1.0 · 2026-10-06 · 前置阅读：`项目需求.md`
> 结论先行：**PHP 8.3 + ThinkPHP 8.0（模块化单应用）+ MySQL 5.7（预留 8.0 升级）+ Redis + React 18 后台 + NativeScript-Vue 3 PDA 端 + 设备接入适配层**

---

## 1. 后端框架：ThinkPHP 还是 Laravel

### 1.1 决策矩阵

| 维度（权重） | ThinkPHP 8.0 | ThinkPHP 6.1 | Laravel 11 |
|---|---|---|---|
| PHP 8.3 官方支持（15%） | ✅ 要求 ≥8.0，8.3 主用 | ⚠️ 要求 ≥7.2.5，8.3 下有弃用告警需处理 | ✅ 要求 ≥8.2 |
| 与团队既有栈一致（25%） | ✅ 同源，现有 `MonaWMS_TX/backend_tp6` 即 TP6.1 | ✅ 完全一致 | ❌ 需重建心智（服务容器/Eloquent/队列写法全换） |
| ORM 与复杂库存事务（20%） | ✅ think-orm 3.x，事务/悲观锁/查询构造器够用 | ✅ think-orm 2.x | ✅ Eloquent 生态最强 |
| 高并发写入适配（15%） | ⚠️ 需自带队列；常驻需 Swoole/Workerman 扩展 | ⚠️ 同左 | ⚠️ 同左（Octane） |
| 生态/包丰富度（10%） | ⚠️ 中等，国内包多 | ⚠️ 中等 | ✅ 最丰富 |
| 部署与国内运维习惯（10%） | ✅ 宝塔/lnmp 直接可跑，文档中文 | ✅ | ⚠️ 需更多队列/调度/Supervisor 配置 |
| 长期维护活跃度（5%） | ✅ 活跃 | ⚠️ 维护为主 | ✅ 活跃 |

### 1.2 选型结论

**主选：ThinkPHP 8.0 + think-orm 3.x（PHP 8.3）**

理由：

1. **团队栈一致是本项目最大的确定性资产。** 现有 `MonaWMS_TX/backend_tp6` 为 `topthink/framework ^6.1` + `think-orm ^2.0` + `firebase/php-jwt ^6.10` + `phpoffice/phpspreadsheet ^1.29`，本项目要复用的不是代码行，而是**已经踩通的部署链路、JWT 中间件写法、统一响应封装、分页约定**。
2. **新项目没有 6.1 的历史包袱，因此直接落在官方当前主线 8.0**：要求 PHP ≥ 8.0，能吃满 PHP 8.3 的只读属性、枚举、`readonly class`、JSON 常量等特性，避免 6.1 在 8.3 上的弃用告警治理成本。
3. **本项目复杂度不在 Web 框架，而在"设备接入吞吐 + 库存一致性"**。这两点靠的是队列、幂等键、事务边界设计，跟选 TP 还是 Laravel 关系不大 —— 用熟悉的那个，把精力留给业务。
4. **多应用/模块化**：使用 `topthink/think-multi-app` 拆 `admin`（后台 API）、`device`（设备上报）、`store`（门店/PDA）、`open`（对外对接）四个应用，边界即鉴权与限流策略边界。

**何时改选 Laravel 11**（触发条件，满足任意两条即建议切换）：

- 需要大量第三方集成包（物流、支付、短信、报表 SaaS）且不想自研驱动；
- 团队 3 人以上具备 Laravel 生产经验；
- 计划做多租户 SaaS 且需要 Sancton/Passport、Jetstream、Octane 等官方组件。

> 备注：**不要** 在同一项目里混用两套框架，也不要把 `monawms-backend`（Go）作为本项目后端主线 —— 需求已明确 PHP 8.3。Go 侧的 RFID 采集思路可借鉴，但语言栈保持单一。

### 1.4 PHP 侧必须落地的工程约定

- 所有 SQL 走 think-orm 查询构造器/参数绑定，**禁止字符串拼接**（库存查询条件多，注入风险高）。
- 库存增减只在 `app/service/stock/*` 内发生，Controller 不得直接改库存表（保证流水与数量同事务）。
- 每个写接口接收 `request_id`（客户端 UUID），落 `sys_idempotency` 表做幂等。
- 分层：`Controller（薄）→ Service（业务）→ Repository/Model（数据）→ Job（异步）`，状态机集中在 `app/service/state/*`。
- 数量一律 `int`（件）+ 金额 `decimal(12,2)`，禁止 float 参与库存计算。

## 2. 设备（RFID）接入架构 —— 本项目的技术核心

固定式读写器/通道门/PDA 的上报方式在国内厂商间差异极大（HTTP POST、TCP 私有协议、串口、SDK 拉取）。因此**必须把设备协议隔离在适配层**，业务层只认统一格式。

```
[通道门/桌面机/PDA/打印机/分拣墙]
        │  各自协议
        ▼
[Device Adapter（可插拔驱动）]
   sim-adapter（默认，开发期用）  ←→  real-adapter（厂商 SDK/HTTP/TCP）
        │  统一读取事件 {device_code, batch_no, epc[], rssi[], antenna, ts}
        ▼
[POST /device/read  （轻校验，<80ms 返回 202，落 Redis Stream）]
        ▼
[Redis Stream / Queue]  ──▶  [Consumer Worker: 去重 → 归集单据 → 差异判定 → 库存事件 → 归档原始日志]
```

| 决策点 | 选择 | 理由 |
|---|---|---|
| 一期接入方式 | 设备 **HTTP 主动上报** 到 `device` 应用（+ 拉取模式兜底） | 最简单可测，PHP-FPM 完全够用 |
| 是否一期就上 MQTT | ❌ 不做；P2 视设备量引入 EMQX/mosquitto | 一期设备量 ≤ 50，HTTP 足够；省掉运维面 |
| 高吞吐兜底 | 若单门 > 600 EPC/min 或多门 > 2400/min 压测不过 → 用 **Workerman/Swoole** 常驻只做"接收+入队"，业务仍在 PHP 常规栈 | 只替换入口层，不动业务代码 |
| 采集服务语言 | 保持 PHP（不引入 Go/Node 微服务） | 需求已定 PHP 8.3；避免多语言运维 |
| 去重 | `read_log` 唯一键 `(device_code, batch_no, epc)` + 时间窗口 | 对应 RF-06/R6 |
| 模拟设备 | 内置 `sim` 驱动 + 命令行 `php think rfid:sim --asn=xxx --count=500 --miss=2` | **关键**：让软件开发不被硬件到货卡住（风险 R1） |
| 分拣墙灯光 | 控制板多为 TCP/串口 → 由独立 `sortwall-agent`（P1）承接，业务侧只发指令到队列 | 隔离硬件抖动 |

## 3. 数据库

| 项 | 结论 |
|---|---|
| 版本 | **沿用现有本地 MySQL 5.7**（需求明确）；生产建议升 8.0（决策项 D2），SQL 保持 5.7 兼容写法 |
| 字符集 | `utf8mb4` / `utf8mb4_general_ci`（5.7 下避免 `utf8mb4_0900_ai_ci`） |
| 引擎/行格式 | `InnoDB` + `ROW_FORMAT=DYNAMIC`（规避 767 字节索引限制） |
| 约束 | 5.7 的 `CHECK` 解析但不生效 → **业务校验全部落在应用层**，DB 只保证主键/唯一/外键语义（外键建议逻辑外键 + 索引，不启用物理约束，便于分库与导入） |
| 索引 | 长文本索引使用前缀（≤191）；EPC `varchar(32)` 全列唯一索引安全 |
| 大表 | `rfid_read_log`（日增百万级）按月分区（ RANGE COLUMNS(created_at) ）或拆表 + 归档任务；统计表走日汇总 |
| 时间 | 存 `datetime`，应用层统一时区 Asia/Shanghai；避免 5.7 的 `CURRENT_TIMESTAMP` 多列限制（仅 created_at 默认） |
| 主键 | `bigint unsigned auto_increment`，业务单号另有唯一索引 |
| 迁移 | `topthink/think-migration` 管理版本化迁移，禁止手工改生产结构 |
| 备份 | 每日全量 + binlog，恢复演练每月 1 次 |

## 4. 前端

| 层 | 选型 | 说明 |
|---|---|---|
| 后台管理 Web | **React 18 + TypeScript + Vite + Ant Design 5 + TanStack Query + Zustand + Recharts** | 与现有 `MonaWMS_TX/frontend` 完全同构（`antd ^5.27`、`@tanstack/react-query ^5`、`react-hook-form ^7` + `zod ^4`、`recharts ^3`），可直接复用脚手架、请求封装、表格/表单范式 |
| 备选 | Vue 3 + Element Plus | 若客户指定或团队更熟 Vue，成本等价；本项目 UI 以表格/表单为主，框架差异不影响交付 |
| 门店/PDA 端 | **NativeScript-Vue 3**（复用 `monawms-mobile`） | 已有工程、构建链路与出包脚本；PDA 需调用厂商 RFID SDK，NativeScript 可通过 Android 原生调用，浏览器/模拟器无法替代真机验证 |
| PDA 备选 | uni-app（现有 `uniapp_frontend`） | 若 Rfid SDK 已有 uni-app 原生插件则优先此路线，成本更低 |
| 状态/数据 | TanStack Query 管理服务端状态，Zustand 只管 UI 状态 | 避免全局 store 膨胀 |
| 实时性 | 通道门读取计数：一期 **2s 轮询**；P1 升级 SSE（`device` 应用暴露 `/device/stream/:gateCode`） | 简单可控 |
| 大屏（P2） | 同 React 工程的一个全屏路由 | 复用组件 |

**前端不做的事**：不在前端实现库存/状态机规则（后端唯一真相源）；分拣墙亮灯指令必须等后端确认后再更新 UI。

## 5. 缓存、队列与定时任务

| 用途 | 方案 |
|---|---|
| 缓存 | Redis 7（`dashboard:*` 60s、字典/权限 30min、单号流水 INCR） |
| 队列 | think-queue + Redis，独立进程：`stock`（库存事件）、`readlog`（原始日志落库）、`print`（打印任务）、`notify`（告警）、`report`（汇总） |
| 定时 | `think\facade\Console` + crontab：日汇总、库龄计算、缺码扫描、心跳判定离线、日志归档、对账 |
| 分布式锁 | Redis SET NX（同 ASN 并发完成、同波次复核） |

## 6. 安全与鉴权

- JWT（Access 2h + Refresh 7d），`device` 应用独立鉴权：设备 token 绑定 `device_code`，不接受用户 token。
- RBAC：菜单权限 + 按钮权限 + **数据范围（全部/本仓库/本门店）**，中间件统一拦截。
- 全链路 HTTPS；PDA 走 4G 时也强制 TLS。
- 密码 bcrypt(cost 12)，登录失败 5 次锁 15 分钟。
- 导出与日志查询脱敏；操作日志不记录密码类字段。
- 依赖扫描：`composer audit` + `npm audit` 纳入 CI。

## 8. 备选方案一览与放弃理由

| 备选 | 放弃理由 |
|---|---|
| 复用 `monawms-backend`（Go）做后端 | 需求明确 PHP 8.3；引入 Go 增加团队维护面。可借鉴其采集层设计 |
| Laravel 11 | 见 §1.2，生态强但团队栈不一致，本项目瓶颈不在框架 |
| MySQL 8.0 直接上 | 客户本地为 5.7，跨版本差异需在 DDL 里规避（`CHECK`、`utf8mb4_0900_ai_ci`、窗口函数）；先兼容 5.7，升级作为决策项 |
| 自研长连接 TCP 网关（一期） | 过度设计；一期 HTTP 上报 + 队列足够，压测不过再补常驻入口 |
| Vue3 后台 | 与现有 React 脚手架二选一即可，不混用 |
| Flutter/uni-app 重写 PDA | 已有 NativeScript 工程与出包链路，除非 SDK 插件缺失才切换 |
| 微服务拆分 | 单仓 + ≤50 门店规模，模块化单体足够；拆服务只增加联调与运维成本 |
